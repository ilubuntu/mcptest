## Overview 总体概述

大屏分栏和模块挪移改变了视觉顺序，却不一定同步改变可访问性结构。页面看起来排列正常，读屏仍可能先到详情操作、再回到列表标题。修复要同时检查语义顺序、可理解名称和可操作性，不能用截图或给每个节点添加相同属性证明读屏正常。

## 问题现象

- 从手机单列切换到展开态或平板分栏后，连续滑动读屏焦点在左右区域之间跳跃。
- 更多、关闭、收藏等纯图标只被读成“按钮”，或读出无意义的资源名称。
- 图标与旁边文字重复朗读，装饰背景也进入焦点序列。
- 整个列表或详情栏被合并成一个节点，内部按钮无法分别操作。
- 缩回窄窗后，焦点仍停在已隐藏或已移走的节点上。

## 适用条件

适用于手机、折叠屏和平板的 ArkUI 页面，且工程已有无障碍验收要求、用户明确提出读屏问题，或当前重排确实影响既有语义。检查本次涉及的区域，不延伸为新增 PC 键鼠或手写笔交互。

## 原因与判断依据

1. **视觉位置与语义组织脱节。** 为方便绝对定位或层叠，代码先声明右栏操作、后声明左栏内容。组件树、分组和可访问性属性共同影响遍历，视觉坐标本身不能保证阅读顺序。应将真实读屏序列与业务阅读顺序逐项比较。
2. **可操作节点没有有效名称。** 纯图标可能缺少名称，但没有显式 `accessibilityText` 并不等于失败：系统控件文字或父级语义可能已经提供名称。判断对象是最终可聚焦节点及其实际朗读结果。
3. **分组或隐藏范围过大。** 父容器启用分组后，子控件可能不再单独获得焦点；`no-hide-descendants` 会连同后代一起隐藏。若按钮视觉可见却不可达，应向上检查这些设置，不能只给按钮补标签。

## 解决方案

### 1. 先整理语义顺序，再处理视觉摆放

明确页面从标题、导航或列表到当前内容、相关操作的阅读路径。按这一逻辑组织组件树和语义区域，让宽窄布局沿用同一业务顺序。不要仅通过坐标、层级或倒置容器摆出正确外观；不要让隐藏布局副本继续暴露为重复读屏内容。

重排组件时保留已有稳定 `.id()` 和业务对象标识，不能为修复顺序随意重命名。切换布局后，原焦点节点仍存在时保持关联；确已消失时，按当前操作上下文落到可理解的有效位置，不无条件跳回首页或页面首项。

### 2. 把名称绑定到真正的操作节点

优先复用系统控件已有文字和语义。没有有效名称的纯图标操作，再补充本地化名称，描述动作而不是图片外观。例如下列 API 12 及以上片段仅展示语义绑定，点击逻辑沿用现有工程：

```typescript
Button() {
  Image($r('app.media.more'))
    .width(24).height(24)
    .accessibilityLevel('no')
}
.accessibilityText($r('app.string.more_actions'))
```

`more_actions` 的文案应表达“更多操作”等真实用途，资源名需替换。内部图标由按钮语义代表，因此不再单独朗读；若图片本身就是信息内容，则不能照此排除。收藏、播放等状态型操作还需使用工程已有状态语义，让读屏能区分当前状态和动作。

### 3. 小范围使用分组和排除属性

`accessibilityGroup(true)` 适合可以作为一个整体理解和选择的内容，例如一组不可独立操作的摘要文字；它不是“分栏都要加”的配置。包含独立按钮、输入框或多条记录的区域，必须确认分组后各操作仍满足交互要求，不能将整栏合并后吞掉子操作。

纯装饰节点可按当前 SDK 使用 `accessibilityLevel('no')`。只有确定整个子树都不应暴露时才使用 `no-hide-descendants`，不得加在仍包含有效操作的容器上。系统或父级已经提供正确名称时，不再重复覆盖，以免朗读重复或状态信息丢失。

## 修复后检查

- 在真实设备开启读屏，连续前进、后退遍历，记录标题、列表、详情和操作的实际顺序；截图不能替代此检查。
- 用读屏执行更多、关闭、选择和提交等关键操作，确认名称可理解、状态正确、没有重复焦点。
- 从单列切换到分栏再缩回，确认焦点不落入隐藏副本，输入与选中项保留。
- 检查分组后的内容能读完整，独立操作仍可到达；装饰节点不产生无意义朗读。
