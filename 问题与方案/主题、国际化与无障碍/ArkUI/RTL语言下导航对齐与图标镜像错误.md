## Overview 总体概述

RTL 适配不是把整个页面水平翻转，而是让布局的阅读起点与终点随语言变化，同时保留品牌、数字、公式和媒体内容自身的含义。文字已经能从右向左显示，并不能证明导航、间距和图标方向正确。

## 问题现象

- 切换 RTL 语言后，返回入口、尾部操作或选中标记仍按原来的左右坐标摆放。
- 文字方向改变，首尾边距、列表缩进和分栏对齐却没有变化。
- 导航箭头没有镜像；品牌、照片、数字或播放图标反而被整体翻转。
- 同一个箭头经过方向适配和手动翻转，出现二次镜像。

## 适用条件

适用于工程已支持或本次明确要求支持 RTL 语言的 ArkUI 页面，覆盖手机、折叠屏和平板。不因页面出现一段阿拉伯语文本就强制改变整个应用方向，也不据此新增语言资源或导航形态。

## 原因与判断依据

1. **把阅读方向写成物理左右。** `left/right` 边距、固定 `x` 坐标或绝对定位表达的是物理位置，无法自动体现“起点／终点”。检查这些值的业务含义，区分需要随语言改变的导航关系与必须保留的物理坐标。
2. **父子方向策略冲突。** 父布局固定为 LTR，局部文本跟随语言；或者已经自动适配，又额外倒置数据顺序、反转容器。应核对实际组件树中的方向属性，而非只检查最内层文字。
3. **镜像范围没有按语义划分。** 箭头所表达的前进、返回关系与品牌、媒体符号不是同一类内容。仅按图片文件类型批量镜像，会破坏不应翻转的内容。

## 解决方案

### 1. 用起点与终点表达阅读关系

将阅读相关的首尾间距替换为 SDK 支持的本地化属性；对齐、锚点和定位也按相同语义处理。普通对称间距不必无意义改写，确有物理左右含义的图形坐标可以保留。

以下片段使用 API 12 起的 `LocalizedPadding` 与 `LengthMetrics`，数值为示意：

```typescript
import { LengthMetrics } from '@kit.ArkUI';

// 位于组件的 build 或 Builder 中
Row({ space: 8 }) {
  Text($r('app.string.next_step'))
    .layoutWeight(1)
    .textAlign(TextAlign.Start)
  Image($r('app.media.arrow_next'))
    .width(20).height(20)
    .matchTextDirection(true)
}
.width('100%')
.direction(Direction.Auto)
.padding({
  start: LengthMetrics.vp(16),
  end: LengthMetrics.vp(24)
})
```

示例箭头资源应是工程约定的 LTR 原始方向，资源名需替换。`LocalizedPadding` 字段不是普通数值类型；低版本工程应沿用兼容封装并核对目标 SDK，不能直接照搬不支持的属性。

### 2. 分开处理布局方向与图像镜像

对确需随阅读方向变化的箭头，可使用 `Image.matchTextDirection(true)`；若已使用 RTL 专用资源，不再额外镜像。品牌标识、照片、视频画面及不应镜像的图标保持原图方向。媒体符号逐项确认含义，不能把所有三角形或箭头归为同一类。

号码、公式等局部内容按其本身语义保持方向和字符顺序，必要时只在该语义区域约束方向，不强制整个页面 LTR。不要手动倒序字符串，也不要对页面根节点使用整体水平翻转来替代 RTL 布局。

### 3. 同步检查宽窄布局分支

检查手机导航、展开态侧栏及已有分栏的首尾关系，沿用原业务顺序，不随意交换主从职责。长翻译仍需换行和弹性容器；方向正确不能代替长文案适配。

## 修复后检查

- 在已支持的 LTR、RTL 语言之间双向切换，核对返回、前进、首尾操作、缩进与文本起点。
- 同时检查方向箭头、品牌、数字、公式、图片和媒体符号，确认无遗漏或二次镜像。
- 覆盖窄窗及本次涉及的宽窗、分栏分支，并使用较长翻译检查截断。
- 组件点击区域与视觉位置一致，路由、选中项和用户输入不因方向切换丢失。
