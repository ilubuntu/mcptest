## Overview 总体概述

深浅色切换后只有部分控件变色，通常不是整个页面没有刷新，而是系统资源、自定义资源和运行态主题值采用了不同的更新路径。应找到未同步的前景、背景或图片，沿用工程已有主题机制修复，不能只把文字改亮而让浅色模式失去对比度。

## 问题现象

- 系统标题栏已进入深色模式，自定义卡片、按钮或弹窗仍是浅色背景。
- 文字、图标与背景接近同色；选中、禁用或按压状态才暴露问题。
- 重进页面后颜色恢复，停留在页面中切换主题却不更新。
- 应用内指定深色后正常，切回“跟随系统”仍保留旧颜色。

## 适用条件

适用于手机、折叠屏和平板中的 ArkUI 页面，且工程已支持或本次要求支持相应主题模式。重点检查自定义颜色、带底色图片、SVG 填充色、自绘内容及动态主题；没有主题能力要求时，不据此新增整套主题功能。

## 原因与判断依据

1. **资源只有一个模式的取值。** 组件引用了自定义颜色键，但该键只定义在 `base` 中，深色模式仍得到同一颜色。需同时核对文字和背景，不能凭缺少 `dark` 目录直接判错：动态主题或其他等效机制可能已经提供正确值。
2. **颜色在初始化时被解析并缓存。** 原本可随配置变化的资源，被提前转换为颜色字面量保存在普通字段中；或者组件仅在首次进入时读取主题。若重进页面能恢复，应重点检查这一链路。
3. **只有主页面消费了主题。** 弹窗、浮层、复用卡片或自绘缓存继续使用旧值。检查实际显示分支，不只查看页面根节点。

## 解决方案

### 1. 统一前景与背景的语义

优先复用现有系统颜色或工程主题 token。自定义颜色按“主文字、次文字、页面底色、卡片底色”等用途命名，不在业务组件散布浅色、深色的硬编码判断。系统颜色资源已有模式适配时，不再加一套手动颜色同步。

若采用资源限定词，在 `resources/base/element/color.json` 与 `resources/dark/element/color.json` 中定义同名键。例如以下两组分别为浅色和深色的示意值：

```json
{"color":[
  {"name":"content_primary","value":"#FF182431"},
  {"name":"surface_card","value":"#FFFFFFFF"}
]}
```

```json
{"color":[
  {"name":"content_primary","value":"#FFF1F3F5"},
  {"name":"surface_card","value":"#FF182431"}
]}
```

值需按产品配色核对，键名和组件引用保持一致。动态主题能提供同等效果时，不要求再重复建立 `dark` 资源。

### 2. 让组件持续消费有效主题

```typescript
Column() {
  Text($r('app.string.card_title'))
    .fontColor($r('app.color.content_primary'))
}
.backgroundColor($r('app.color.surface_card'))
```

示例资源名需替换为工程实际资源。采用运行态主题时，让颜色来自已有可观察主题状态，并在主题变化后更新对应消费者；不要把资源解析结果永久缓存，也不要为每个页面重复创建配置监听。

### 3. 补齐非文字资源和切换路径

检查图片本身是否带白底、图标是否内嵌固定填充色，以及遮罩透明度、边框和禁用态是否仍可辨认。需要重绘的自绘内容应使旧缓存失效。沿用“应用内浅色／深色／跟随系统”的既有规则，避免页面局部强制模式覆盖应用选择。

不要通过重建整个页面修复颜色同步，以免清空输入、选中项或滚动位置。

## 修复后检查

- 在同一页面连续切换浅色、深色，再切回跟随系统；正文、背景、图标及当前弹窗同步更新。
- 检查普通、选中、禁用和按压状态，不能只检查静态正文。
- 在本次涉及的窄窗和宽窗分支检查自定义内容，确认不同分支没有遗漏主题绑定。
- 切换前后路由、表单内容和阅读位置不变；重新进入页面也没有恢复成旧主题。
