# ArkUI 宽屏页面窄条留白、列表不增列与图片过大

## Overview 总体概述

展开或在平板上运行后，页面可能仍缩成手机宽度，也可能把一张卡片放得很大却没有显示更多内容。需要先区分“尺寸没更新”和“布局策略未调整”，再根据列表、表单、正文等内容选方案。两侧留白不必然是缺陷，阅读正文或窄表单的合理限宽应保留。

## 问题现象与适用条件

- 标题、导航、列表一起缩在中间窄条，两侧空白很大。
- 商品列表仍为单列，卡片图片随宽度放大，占据大半屏。
- 已配置多列，但实际设备达不到生效档位；或一栏窄到文字难以阅读。

适用于 ArkUI 宽屏业务内容区域。原方案明确单列阅读或少量固定入口时，不以“必须增列”作为判错标准。

## 原因与判断依据

1. 检查根容器及中间包裹层的固定宽度、maxWidth、百分比和 span；定位是哪一层限制了内容，而不是直接取消全工程限宽。
2. 若容器已铺满，检查列表 lanes、网格 span、WaterFlow 列模板或 Swiper 显示数量是否仍为窄屏值。
3. 结合卡片最小可读宽度、项数、间距和窗口高度计算列数。相同宽度的折叠屏与平板不应仅凭型号强行使用不同列数。
4. 核对断点实际范围。把三列仅配置在 xl，而目标窗口始终位于 lg，会使这套策略永远不生效；这不等于每个更大档位都必须增加一列。

## 解决方案

### 同质列表增加可见内容

结构相同的 ListItem 可使用 List 的 `lanes`；规则卡片使用 GridRow/GridCol；高度差异大的内容可使用 WaterFlow。混合表单、章节正文和固定头栏不能直接当成同质列表增列。

下面是已计算列数后的 List 片段，`columnCount` 根据内容区实际宽度及最小卡片宽度产生，`items` 沿用稳定业务 ID：

```ts
List({ space: 12 }) {
  ForEach(this.items, (item: ItemData) => {
    ListItem() {
      this.itemCard(item)
    }
  }, (item: ItemData) => item.id)
}
.lanes(this.columnCount)
.width('100%')
.height('100%')
```

切换列数后检查分割线、间距、滚动锚点及选中状态；不能通过重建全部业务数据来重置页面。WaterFlow 还需核对目标版本的布局模式和列模板更新行为，不能把某个版本的重排表现当成所有版本都一致。

### 表单和正文按语义调整

- 长表单可以按相关字段分组挪移，不能为凑双列把存在顺序关系的输入拆散。
- 详情正文可按可读行长限宽；标题栏、导航、页面背景是否跟随收窄，由原设计分别决定，不能把整个页面无意缩成一条。
- GridCol 的 span/offset 可表达局部缩进；`constraintSize({ maxWidth })` 也可用于合理的内容上限，两者不是互相排斥的“唯一正确”写法。
- 限宽对象若是整个阅读视口，限宽层包住 Scroll；若仅某个段落限宽，放在 Scroll 内。两种写法滚动条和点击区域不同，应按需求选择。

### 不借增列擅自改导航结构

列表增列与列表—详情分栏不是一回事。原页面为 Stack，且用户未要求主从分栏时，先保持路由语义；不要因为窗口变宽就引入 Navigation Auto/Split。已确认双栏时，再分别处理栏宽、默认内容和返回逻辑。

## 相关方案

页面窄条若来自 Navigation 自身分栏，读《ArkUI Navigation 宽屏主页变窄、右栏空白与跳转白屏》；若容器已铺满而轮播信息量未增加，读《ArkUI Swiper 宽屏仍单项、轮播拉长与边缘留白》。不要只取消限宽来处理这两类原因。

## 修复后检查

比较窄屏、目标宽屏和局部分屏：信息量是否按方案增加，卡片是否仍可读，图文比例是否合理。检查少量数据、空数据和返回滚动位置；不能只以左右没有空白判断适配完成。
