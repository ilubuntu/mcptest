# ArkUI 窗口与容器断点不一致导致网格不变、分栏截断

## Overview 总体概述

窗口很宽，不代表某个卡片区也很宽。侧栏、系统分屏或平行视界会缩小内容区域；局部网格仍按整窗断点增列，就会截断。另一类问题是断点名称、边界和栅格份数不匹配，导致大屏始终沿用窄屏排列。

## 问题现象与适用条件

- 展开或拉宽后网格列数不变，图片却越来越大。
- 大窗口中的局部栏很窄，网格仍显示多列，文字和按钮被压缩。
- 到某个边界突然恢复手机布局，或配置了 xl 却始终没有进入。

适用于 GridRow/GridCol 及消费断点状态的 ArkUI 自定义布局。先确认该区域确实应随可用空间变化，不能仅凭设备型号判定列数错误。

## 原因与判断依据

1. **参考对象错误**：整页导航可根据窗口决策；栏内卡片通常应按所属容器决策。查看 `breakpoints.reference`，同时比较窗口宽度和 GridRow 实际宽度。
2. **自定义档位与消费端不匹配**：N 个有效边界产生 N+1 档，自 xs 依次命名。只有两个边界时没有后面的 lg/xl 档；较少边界本身合法，错在消费端仍假定这些档位存在。
3. **份数含义弄错**：`columns` 是总栅格份数，`span` 是每项占几份，不是卡片列数。每项占 6/12 时约为两列；offset 和间距也会影响排布。
4. **状态不刷新**：GridRow 已回调新断点，但消费端保存的是初始化快照，或自定义断点源没有响应窗口、密度变化。此时应修状态订阅，不是继续增加边界。
5. **遗漏端点**：只判断 `isLg`，没有处理 xl；或 xs 落入缺省分支。检查真实配置覆盖的全部区间以及正反方向切换。

## 解决方案

### 局部栅格按自身宽度决策

以下为自定义五档、统一十二份的示例，不是所有工程必须采用的断点表：

```ts
GridRow({
  columns: { xs: 12, sm: 12, md: 12, lg: 12, xl: 12 },
  gutter: { x: 12, y: 12 },
  breakpoints: {
    value: ['320vp', '600vp', '840vp', '1440vp'],
    reference: BreakpointsReference.ComponentSize
  }
}) {
  ForEach(this.items, (item: ItemData) => {
    GridCol({ span: { xs: 12, sm: 12, md: 6, lg: 4, xl: 3 } }) {
      this.itemCard(item)
    }
  }, (item: ItemData) => item.id)
}.width('100%')
```

`items`、`ItemData` 和卡片构建函数沿用业务定义。示例列数为 1/1/2/3/4，采用前须确认卡片在对应宽度下放得下；不能把这组列数当成直板、双折、三折和平板的固定映射。

### 统一配置与状态含义

- 自定义边界采用递增的 vp 值，消费端使用同一组定义；不混用一套系统档位名称和另一套手算边界。
- 明确最小档 span、总份数及需要用到的其他档位，避免依赖未核对的继承或默认值。系统允许使用默认配置，不应将未显式填写 `columns` 直接判为缺陷；默认值可能随 API 版本不同。
- 同一测量范围共享一份断点状态；局部容器有自己的宽度条件是合理的，不应强行共用整窗状态。
- 需要高度策略时单独判断可用高度。横向 lg 并不保证窗口足够高。

## 修复后检查

检查每个实际配置边界两侧、最窄窗口、局部分栏和最大窗口；宽变窄、窄变宽都要恢复正确。核对真实卡片列数、文字宽度和点击范围，而不仅看断点日志。若 GridRow 收到的新宽度正确、页面仍旧，继续检查响应式状态消费和后续固定尺寸覆盖。
