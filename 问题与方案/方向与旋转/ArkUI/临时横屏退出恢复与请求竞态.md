## Overview 总体概述

视频、直播、图表等页面临时请求横屏，会修改整个窗口的方向策略。页面返回不会自动撤销这个副作用。正确恢复的是进入前的策略，而不是当时看到的物理角度；方向写入还必须统一排序，否则旧页面的异步请求可能在返回后覆盖恢复值。

## 问题现象

退出横屏页后首页仍保持横屏；外屏进入播放页、展开后返回，首页反而被锁回旧竖屏；快速进入退出时方向闪动或偶发反向；Tabs 中切换页面后策略没更新。旋转时还可能出现白屏、卡顿、页面重置或重复初始化。

## 适用条件

适用于原生 ArkUI 非取流页面的临时方向修改，包括 Router、较早版本 Navigation，以及 API 19+ 不满足页面级声明条件的页面。若已经采用满足条件的 NavDestination.preferredOrientation，应由系统按目的页交接，不再叠加本篇手动保存恢复路径。

## 原因与判断依据

setPreferredOrientation 是窗口级状态，不是某个组件的私有属性。display.rotation、Display.orientation 描述当前状态，折展后自然方向或当前显示区域可能改变；把进入时角度翻译成固定 PORTRAIT、LANDSCAPE 再恢复，会丢掉原本“跟随桌面”或“自动旋转且尊重旋转锁”的语义。

另一个问题是生命周期不匹配：Navigation 目的页可能隐藏但仍驻留，Tabs 子组件可能只在首次创建时触发 aboutToAppear。只在创建/销毁时设置方向，无法表达显示/隐藏和页签激活。若多个回调分别写窗口方向，或者未等待一次请求完成便发起下一次，离场恢复也可能被旧横屏请求覆盖。

## 解决方案

### 先确定唯一控制路径

API 19+ 的页面级属性只有在全屏主窗口、Navigation 占满应用页面、NavDestination 为 STANDARD 时生效。各参与交接的目的页声明自己的策略，启动基线仍由 Ability 配置。Router、局部 Navigation、DIALOG 或多窗场景不能直接套用该能力；不要为了接入它主动改变原有导航结构。

手动路径进入时从主窗口 getPreferredOrientation 保存策略枚举，该查询接口从 API 12 起支持。更早系统由工程现有方向管理器记录已经设置的策略，不能调用不可用接口或猜一个默认值。查询失败时记录错误并采用明确降级，不在没有保存成功的情况下先覆盖窗口再随意恢复。

### 保存策略，并把进入与退出加入同一队列

下面是合入已有窗口管理器的最小单会话示例，适用于 API 12+。win 为管理器持有的主窗口；队列只负责串行交接和丢弃尚未执行的旧请求，不取消已经发出的系统调用。多层页面必须由同一管理器维护所有权或策略栈，不能每页各建一个实例。

```typescript
import { window } from '@kit.ArkUI';
import { BusinessError } from '@kit.BasicServicesKit';

class TemporaryOrientationSession {
  private win: window.Window;
  private revision: number = 0;
  private saved: window.Orientation | undefined = undefined;
  private overridden: boolean = false;
  private queue: Promise<void> = Promise.resolve();

  constructor(win: window.Window) { this.win = win; }

  enter(target: window.Orientation): Promise<void> {
    const revision = ++this.revision;
    this.queue = this.queue.then(async () => {
      if (revision !== this.revision) { return; }
      if (this.saved === undefined) {
        this.saved = this.win.getPreferredOrientation();
      }
      this.overridden = true;
      await this.win.setPreferredOrientation(target);
    }).catch((error: BusinessError) => {
      console.error(`orientation enter: ${error.code}, ${error.message}`);
    });
    return this.queue;
  }

  leave(): Promise<void> {
    ++this.revision; // 未执行的旧进入任务将被跳过
    this.queue = this.queue.then(async () => {
      if (this.overridden && this.saved !== undefined) {
        await this.win.setPreferredOrientation(this.saved);
        this.saved = undefined; // 恢复失败时保留待处理状态
        this.overridden = false;
      }
    }).catch((error: BusinessError) => {
      console.error(`orientation restore: ${error.code}, ${error.message}`);
    });
    return this.queue;
  }
}
```

进入请求已经发出时，即使 revision 变化，也不能认为系统请求被取消；leave 排在其后完成恢复。相同目标去重应放在共享管理器中，但只有请求实际成功后才记录“已应用”，失败后不能因错误缓存永远跳过重试。恢复失败应让已有管理器按当前页面所有权处理或提示降级，不增加无限重试定时器。

不统一恢复为 PORTRAIT、AUTO_ROTATION 或 UNSPECIFIED(0)。如果保存值是 FOLLOW_DESKTOP，就恢复它，让系统根据返回时的当前形态重新决定方向。嵌套横屏页返回时应恢复上一有效页面的策略；旧页面释放时只有仍持有控制权才能写回，不能把已被新页面接管的窗口恢复成更早状态。

### 交接点匹配真实可见性

Router 页面使用工程既有显示/隐藏机制；Navigation 手动路径在实际 onShown/onHidden 等交接点处理；Tabs 根据活动页签变化处理，不把每次 Swiper 内容切换都当作重新进入页面。页面缓存并不表示仍应持有窗口方向控制权。

异步取得窗口前记录会话编号，返回后检查页面仍激活。离开后禁止旧初始化继续注册监听或发起进入方向请求。显示尺寸监听 on/off 保持同一回调引用，初始读取 windowRect 和后续 windowSizeChange 使用同一同步方法。横屏状态进入媒体页时尺寸可能不再变化，不能只挂监听等待第一次旋转才更新全屏布局。

### 旋转后白屏、重置与卡顿分别处理

先确认路由或组件是否真的重建，不假定每次旋转都会销毁整个页面。保留输入、路由、Scroller、媒体控制器，避免在尺寸回调中重新 loadContent、清空业务状态或重跑网络初始化。确需重建时，在组件就绪后恢复阅读锚点、进度及播放/暂停状态，并用会话序号阻止旧恢复覆盖新操作。

如果页面实例未重建但仍卡顿，检查窗口变化回调中的同步计算、图片处理和重复资源初始化。只更新发生变化的约束，耗时且可脱离 UI 的计算再按 taskpool 的可传输数据与线程约束转移；UI 状态更新仍在对应 UI 上下文处理。freezeWhenInactive 面向非活跃组件的冻结行为，不是所有旋转卡顿的通用开关，也不能代替状态连续性。

## 修复后检查

- 原策略分别为固定、跟随桌面、自动旋转时，临时横屏退出恢复原策略，而非固定物理方向。
- 外屏进入、展开后返回，以及连续两层临时页面返回，符合当前形态和有效页面策略。
- 快速进入退出、切 Tabs、后台返回后，没有旧任务覆盖当前页面，没有重复窗口监听。
- 横屏直接进入时全屏布局立即正确；旋转期间输入、阅读位置、播放与暂停状态保持连续。
