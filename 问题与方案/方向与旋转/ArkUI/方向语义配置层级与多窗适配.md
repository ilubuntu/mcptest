## Overview 总体概述

“设备转了”“窗口横向”“页面允许横屏”并不是同一个判断。方向策略决定应用希望怎样旋转，窗口和容器尺寸决定内容如何布局。先核对策略语义、配置归属与当前窗口模式，再处理尺寸同步和布局变体，才能区分强制竖屏、策略不生效、旋转后留白与图片裁切。

## 问题现象

折叠展开态或平板仍被锁成手机竖屏；分屏、悬浮窗里调用旋转接口成功却没有转向；旋转后内容仍按旧方向排布，底部或右侧多出空白；180° 后某些方向相关元素不更新；轮播图片或文字在横竖切换后截断。

## 适用条件

适用于手机、折叠屏和平板的原生 ArkUI 主窗口与页面方向适配。页面级属性针对 Stage 模型、API 19+ 的 Navigation；Router 和不满足页面级前提的页面继续使用既有窗口级控制。本篇不把分屏与悬浮窗等同于全屏，也不以更换配置层级绕过系统窗口限制。

## 原因与判断依据

三类值不能直接互换：window.Orientation 是可设置的策略；Display.orientation 是当前显示方向状态；Display.rotation 是相对自然方向的旋转量，取值表示若干个 90°，不是窗口横竖屏枚举。自然方向受设备形态影响，rotation 为零不保证是竖屏，不能将其强制转换为 Orientation 恢复窗口。

页面布局看窗口或父容器的真实宽高。折叠设备的 deviceType 也可能返回 phone，仅凭这个字符串锁竖屏会误伤内屏。getFoldStatus 返回 UNKNOWN 也不能区分直板手机与平板。显示大小、密度变化会改变逻辑尺寸，既不能用固定 vp 阈值猜旋转能力，也不能换成某个固定 px 阈值冒充通用修复。

## 解决方案

### 按职责选择配置层级

| 层级 | 放置位置与作用 | 适用边界 |
| --- | --- | --- |
| 启动基线 | 目标 module.json5 的 abilities 节点配置 orientation | 对应 UIAbility 的启动策略，多入口分别核对 |
| 运行时窗口策略 | Window.setPreferredOrientation，API 9+ | 影响同一窗口全部页面，临时修改需要交接与恢复 |
| Navigation 页面声明 | NavDestination.preferredOrientation，API 19+ | 全屏主窗口、Navigation 占满应用页、STANDARD 目的页同时满足 |

这不是三套可以任意同时写入的优先级链。全应用方向一致时优先声明启动基线，避免先按默认方向启动、随后才调用 API 造成启动旋转。页面间确有差异时选择一种动态控制入口；不要在页面声明策略的同时，又让页生命周期和全局回调反复调用窗口接口。

需求如果逐形态与桌面一致，可选 FOLLOW_DESKTOP(17)：它跟随桌面的旋转模式，不等于无条件四向旋转。声明片段放在实际生效的目标 Ability 中，保留原有其他字段：

```json5
{
  "name": "EntryAbility",
  "orientation": "follow_desktop"
}
```

FOLLOW_DESKTOP 从 API 12 起支持。不要看到“折叠屏”就直接选它，仍需核对目标形态的桌面行为与产品要求。若某形态明确要求不同于桌面的方向，再复用既有管理器做业务分支，不在修复局部问题时另建整套设备判定。

### 区分几个容易混淆的策略

| 策略 | 数值 | 关键区别 |
| --- | ---: | --- |
| PORTRAIT | 1 | 固定竖屏，不是“先竖屏后可自动转” |
| AUTO_ROTATION | 5 | 四向自动旋转，不受系统旋转锁限制 |
| AUTO_ROTATION_RESTRICTED | 8 | 四向自动旋转，受旋转锁控制 |
| AUTO_ROTATION_LANDSCAPE_RESTRICTED | 10 | 两个横向之间自动旋转，受旋转锁控制 |
| AUTO_ROTATION_UNSPECIFIED | 12 | 自动旋转且受锁控制，允许方向还由系统与产品形态决定 |
| USER_ROTATION_LANDSCAPE | 14 | 先请求横屏，随后遵循传感器、旋转锁和系统允许方向 |
| FOLLOW_DESKTOP | 17 | 跟随桌面旋转模式 |

UNSPECIFIED(0) 只是未定义方向模式，不是上述策略的同义词，也不是万能重置值。窗口设置接口从 API 9 起支持，不表示每个较新枚举从 API 9 都可用，须同时核对枚举版本与目标系统。

### 多窗中以布局适配为主

主窗口非全屏时，策略设置可以成功但不立即引发方向改变；分屏、智慧多窗悬浮窗等场景由系统按窗口规则处理，返回全屏后才可能重新评估。接口成功只表明调用完成，不证明页面已旋转。不要在尺寸回调里持续重试，或者改用 NavDestination 属性强行绕过。

这些窗口中用 windowSizeChange 更新窗口约束，局部内容用 onAreaChange；短宽窗口可改为横向排列、让次要区滚动、减少非必要留白。宽度与高度都应参与设计判断，不能只因窗口达到宽断点就强制分栏，也不能未经业务确认改变已有 Navigation 的 Stack/Split 语义。

### 旋转后同步布局，而非只同步方向标签

初始化读取一次 windowRect，再注册后续尺寸监听，两者进入同一个更新函数。windowSizeChange 的回调直接给出新宽高，使用回调参数，不在 display change 中立即查询显示器宽高来代替窗口尺寸：显示属性可能仍处于更新过程，且显示器尺寸也不等于分栏容器尺寸。

旋转不一定跨越宽度断点。宽度断点没变但高宽比或可用高度变化时，应更新对应的高度约束、布局变体；List、Scroll 的父链需有界高度，可用 layoutWeight(1) 分配剩余空间，不能让内容无限撑高后期待滚动自动生效。

180° 旋转通常不改窗口宽高，不能期待 windowSizeChange 一定触发。先确认页面策略、旋转锁及设备允许方向；普通响应式页面无需为此额外监听。只有自定义定位、绘制或方向相关内容确实依赖当前显示方向时，再消费 display change 的方向状态，并保存回调引用成对注销；布局宽高仍由窗口或区域数据提供。

轮播裁切还要检查媒体约束：图片不能只设宽度任由原图比例放大高度；使用 aspectRatio 或有明确含义的高度上限，按产品选择 Contain 全图或 Cover 裁剪，避免 Fill 拉伸。Swiper 是重复内容容器，若宽屏要求同时显示多项，应联动 displayCount、itemSpace、indicator 和边缘露出；prevMargin、nextMargin 不是项间距。不能把整条轮播限成一张窄图来掩盖尺寸更新错误。

## 相关方案

临时横屏页面退出后其他页面仍保持错误方向时，读《ArkUI 临时横屏退出恢复与请求竞态》；实际方向已正确但宽高仍旧时，读《ArkUI 窗口切换后尺寸不更新、布局留白或监听重复响应》。

## 修复后检查

- 直板、折叠内外屏和平板分别核对策略，系统旋转锁开关变化符合产品预期。
- 全屏转分屏、悬浮窗再返回，页面按新窗口约束可用，没有接口重试造成方向互搏。
- 90°、180° 分别验证，区分需要方向监听的自定义内容与仅需尺寸适配的普通页面。
- 显示大小、大字号、短窗口下，列表末尾可达，轮播比例和文字不被非预期裁掉。
