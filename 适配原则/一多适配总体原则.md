## Overview 总体概述

折叠屏展开、平板横屏或进入分屏后，页面既不能出现非预期截断、按钮被挤出屏幕，也不能只把手机内容整体放大。应先检查内容实际得到的宽高，再决定伸缩、换行、增列或重新排列；布局变化后，用户已填写的内容、正在阅读的位置和播放进度仍需保留。

## 1. 先检查内容实际得到的宽高

页面留白、显示不全或滚不到底时，沿“应用窗口 → 页面根容器 → 业务区域 → 父容器 → 目标组件”检查宽高、边距和其他控件占位，找到第一处与预期不符的位置。混合工程还需检查 Web、RN、Flutter 宿主是否把新尺寸传递给页面。

例如内容已设为填满，父容器却仍固定为手机宽度，内容就无法利用展开后的空间。应先修父容器，而不是继续给内部组件增加宽度补丁。

- **尺寸有参照。** 百分比或填满相对哪一层、哪条方向计算，需要按框架确认；最小、最大尺寸只是上下限，不是实际测量值。弹性分配也需要父布局支持，并有可分配空间。
- **区分占位与覆盖。** 示例：有效高度 720，标题占 64、底栏占 56，中间剩余 600；中间仍取整页 720，就可能越界。示例使用同一单位，不是控件规格。浮层不参与正常占位，需另外处理遮挡；安全区、键盘和边距已计入有效区域时，不重复扣除。
- **分开滚动区域和内容。** 可见的滚动区域需要明确边界，内部内容可以更长。不要把内容也限成一屏，或在每层盲目增加滚动。嵌套滚动明确方向，末项不能被底栏挡住。

固定尺寸不一定有错，合理的图标大小、阅读宽度和业务约束可以保留。各框架的百分比、弹性和无界空间处理不同，不能照搬同名属性或用隐藏溢出掩盖问题。

## 2. 按页面内容调整排列

先判断内容是否重复、有无列表与详情关系、哪些操作必须保留，再结合容器实际宽高选择布局。设备类型或断点本身不决定列数、侧栏和分栏；悬停、折痕分区还需设备能力及实际分区信息。

| 页面情况 | 可采用的处理 | 需要注意 |
|---|---|---|
| 结构不变，只是按钮或局部内容排不开 | 伸缩、均分、换行，必要时滚动 | 不把字号、图片和间距一起无限放大 |
| 商品、卡片等同类内容较多 | 增加列表或网格列数 | 按栏内宽度、条目最小可读宽度、间距和数量计算，不因跨断点就强制增列 |
| 上下排列在宽短窗口中拥挤 | 调整为左右排列，或挪移模块、导航 | 保持阅读与焦点顺序；导航变化沿用原有设计和本次修改范围 |
| 业务需要同时查看列表与详情等内容 | 主从分栏或不同职责区域并排 | 保留选中项、路由和返回行为，缩回窄窗后入口仍能使用 |
| 长篇正文或有明确操作宽度要求的区域 | 局部限宽 | 不默认把整页背景、导航、列表和可扩展区域都收成窄条 |

图片比例、裁切方式和占屏大小分别判断：比例正确，仍可能因高度过大挤掉操作区。不要用新增无关模块或放大装饰内容填空。宽屏增强后，窄窗下的正文、入口和操作不能直接消失；长文案、大字体、读屏及焦点顺序也需兼顾。

## 3. 窗口变化后保留用户进度

用户正在填表、浏览列表或播放视频时，折展、旋转和分屏应调整布局，而不是回到首页、清空输入或从头播放。退出登录、切换业务对象等有意重置，不属于这类问题。

- **保留业务状态。** 当前页面、路由参数、输入、选中项和业务进度，不应随临时布局分支一起销毁；沿用工程已有的状态保持方式，不默认写入磁盘。
- **按内容恢复位置。** 列表从两列变四列，原滚动距离可能指向另一条记录。先记录阅读项目或业务锚点，新布局可测量后再恢复位置；焦点和弹层也不能指向已经移走或不可见的控件。
- **业务状态与资源分开。** 尺寸变化不等于必须重启相机、播放器或整页。确需重建时，保留播放进度、前后摄选择等意图，不复用失效的 Surface、相机 ID、句柄或输出规格；新资源和布局就绪后再恢复允许延续的操作。
- **防止旧结果回写。** 连续变化后只采用最后一次有效状态，旧回调和异步创建结果不能覆盖新状态。离场时清理监听、无效任务和资源，返回时重新核对当前尺寸与能力。

检查时可先填写表单、定位一条记录或开始播放，再执行本次涉及的折展、旋转或分屏，确认布局和业务进度均正确，反向切回后也没有旧状态回写。

以上是跨框架的判断方法；具体组件、API、版本限制及问题修法放在对应框架的问题与方案中。设备分类、单位和断点定义仍由公共规则统一维护。
